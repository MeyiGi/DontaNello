# Dontanello: архитектура развития

Статус: внедрены completion, reports и operations. Telegram принимает команды из настроенного личного чата; отчёты, расписание, локальные копии и уведомления реализованы. Политики доставки и восстановления описаны в [ADR 0002](decisions/0002-reports-and-operations.md), первый формат через Groq — в [ADR 0003](decisions/0003-groq-narrative-reports.md), структурированные обзоры прогресса — в [ADR 0004](decisions/0004-progress-reviews.md), анализ через Groq — в [ADR 0005](decisions/0005-groq-progress-analysis.md).

## Цель

Добавлять независимые автоматизации, интеграции и способы управления с локальными изменениями. Уменьшать связанность и стоимость сопровождения. Будущий переход к микросервисам допустим, но простоту эксплуатации сохраняем сейчас. Архитектура не гарантирует постоянную стоимость любой новой функции: сложные связи требуют явного проектирования.

## Решение

Модульный монолит на Python, модули по возможностям, внутри — порты и адаптеры. Один репозиторий и первоначально один сервис. Планировщик, Telegram и CLI запускают одни и те же прикладные сценарии. Внешние API подключаются через адаптеры; бизнес-правила не знают об HTTP или формате Notion.

Основание: [Monolith First, Martin Fowler](https://martinfowler.com/bliki/MonolithFirst.html) и [Ports & Adapters, Alistair Cockburn](https://alistair.cockburn.us/hexagonal-architecture). Это выбранная для данного проекта схема, а не обещание автоматического превращения монолита в микросервисы.

## Структура по мере появления функций

```text
src/dontanello/
  bootstrap.py                 # сборка конкретных зависимостей
  entrypoints/
    cli.py
    telegram.py                # команды, проверка пользователя, маршрутизация
    worker.py                  # расписание, запуск сценариев, изоляция ошибок
  modules/
    completion/
      models.py                # типизированные наблюдения и решения
      application.py           # переход чекбокса → дата
      ports.py                 # источник наблюдений, запись даты, состояние, часы
      adapters/
        notion.py              # поля Notion ↔ внутренние типы
        json_state.py          # сначала сохраняем текущий формат состояния
    reports/
      application.py
      progress.py              # общий pipeline фактов и проверок
      strategies.py            # Weekly / Monthly: разные цели анализа
      progress_models.py       # доказательства, цитаты, структурированный документ
      progress_ports.py        # анализ, архив, стратегии
      narrative.py             # прежний формат: совместимость и тесты
      delivery.py              # долговечный журнал попыток доставки
      schedule.py              # календарные периоды и пропущенные запуски
      ports.py                 # чтение выполненного за период, доставка отчёта
      adapters/
        groq_progress.py       # Groq: последовательные пакеты, синтез, проверка цитат
        sqlite_progress.py     # версионированный архив обзоров
        groq.py                # прежний SummaryGenerator
    operations/                # резервные копии и уведомления об ошибках
  integrations/
    notion/client.py           # HTTP, ограничения API, пагинация; без правил задач
    telegram/client.py         # транспорт Telegram; без правил отчётов
    groq/client.py             # HTTP Groq, ограниченный failover ключей при 429
  platform/                    # настройки, часы, логирование, управление ресурсами
tests/
  unit/
  contracts/
  architecture/
docs/decisions/
```

Не создаём пустые каталоги для гипотетических функций. Порт определяется потребностями конкретного сценария; адаптер может использовать общий клиент интеграции. Не вводим общий интерфейс «любой сервис» или «любая автоматизация».

## Зависимости и владение

- Точки входа вызывают application; application зависит от своих моделей и портов.
- Адаптеры реализуют порты и обращаются к внешним клиентам или локальному хранилищу.
- Bootstrap связывает реализации с потребителями. Он может импортировать все стороны; бизнес-код не импортирует bootstrap.
- Один модуль обращается к другому через его публичный контракт. Циклы запрещены. Межмодульный процесс координируется отдельным прикладным сценарием, если это действительно необходимо.
- Каждый модуль владеет своим состоянием. Совместное использование файла БД допустимо, чтение чужих таблиц напрямую — нет.

Пример расширения: отчёт собирает выполненные записи за период через порт чтения и отправляет текст через порт доставки. Telegram — один адаптер доставки. Добавление email меняет адаптер и сборку зависимостей; правила периода и построения отчёта сохраняются.

## SOLID, DRY, KISS на практике

| Принцип | Правило проекта |
|---|---|
| SRP | API-клиент, сценарий, хранилище и точка входа имеют разные причины изменения. |
| OCP | Новая реализация внешней зависимости подключается через порт; не требуем отсутствия любых изменений существующего кода. |
| LSP | Адаптеры соблюдают общий контракт результата, ошибок и побочных эффектов. |
| ISP | Потребитель зависит только от нужных операций; нет универсального клиента со всеми методами. |
| DIP | Сценарий задаёт контракт; конкретный API/БД его реализует. |
| DRY | Правило периода или выполнения определяется один раз. Разные по смыслу сценарии не объединяются из-за похожих строк. |
| KISS / YAGNI | Прямые вызовы, явная сборка и минимальная инфраструктура до появления измеримой необходимости усложнения. |

Основные паттерны: Adapter для внешних API; Repository для состояния; явное внедрение зависимостей. Strategy добавляем при нескольких взаимозаменяемых правилах. События и Outbox — когда нужна надёжная асинхронная связь. Паттерн должен решать названную проблему, а не увеличивать число классов.

## Хранение, расписание и надёжность

JSON текущего watcher сохранён без изменения ключей. Отчёты владеют SQLite-журналом доставки с WAL; остальные модули сохраняют собственное состояние. PostgreSQL понадобится при нескольких хостах или требованиях, которые SQLite не закрывает; сейчас его не вводим.

Для каждого задания задаём часовой пояс, период, правила пропущенных запусков, повторов и отключения. Планировщик не содержит правила построения отчёта. Ключ отчёта включает получателя, тип и период. Журнал попыток и доставки предотвращает обычные дубли, но не устраняет неопределённость, когда внешний API принял сообщение, а подтверждение потерялось. Политика такого повтора должна быть явной.

Журналы содержат имя задания, время, результат, попытку и длительность без секретов. Groq transport переключает настроенные ключи только при явном 429; неуспешные попытки входят в бюджет анализа. Активный ключ и временные ограничения хранятся в памяти с защитой одновременного доступа, после перезапуска основной ключ проверяется снова. Общая квота организации может ограничить весь пул; сетевая неопределённость или 5xx не вызывают переключения. Отказ Notion не должен останавливать независимую автоматизацию. Для долгих и блокирующих задач выделяем независимый исполнитель, когда они появляются; не помещаем все функции последовательно в один бесконечный цикл.

## Возможное выделение микросервисов

Причина выделения: отдельное масштабирование, граница безопасности, независимое развёртывание или сильная изоляция отказов. Большое количество функций само по себе не является достаточной причиной.

Порядок выделения модуля:

1. Зафиксировать его публичный контракт, зависимости и владение данными.
2. Убрать обращения к внутренностям и чужому хранилищу.
3. Определить сетевые ошибки, тайм-ауты, аутентификацию, версии контрактов и повторную доставку.
4. Заменить вызов через порт сетевым адаптером, вынести процесс и собственное хранилище.
5. Проверить деградацию, восстановление, мониторинг и стоимость эксплуатации.

Сеть меняет семантику вызовов: извлечение требует работы даже при хороших границах. Для событий предполагаем возможность повторной доставки; потребитель идемпотентен. Транзакция локальной БД не распространяется на внешний API. Outbox добавляется для согласованной фиксации локального изменения и исходящего события, когда это требуется. Общая БД с прямыми межсервисными запросами подрывает независимость.

## План перехода текущего кода

1. Выполнено: поведение completion покрыто тестами, включая повтор, сбой записи, перезапуск и часовой пояс.
2. Выполнено: completion вынесен в пакет, типизированный сценарий отделён от Notion и состояния. `assistant.py` сохранён как совместимая точка входа systemd.
3. Выполнено: настройки и сборка зависимостей отделены; настроены Ruff, mypy и тесты запрещённых импортов и циклов.
4. Выполнено: Telegram с проверкой настроенного личного чата и тонкими обработчиками команд.
5. Выполнено: reports, SQLite-журнал доставки, политика повторов/неопределённого результата, расписание и operations с копиями/уведомлениями.

При переносе не менять даты, чекбоксы, ключи сохранённого состояния или baseline. Миграция хранилища требует резервной копии, теста и безопасного возврата. Архитектурный рефакторинг и новые правила выполнения оформлять отдельными изменениями, где возможно.

## Проверяемое качество

Unit-тесты сценариев выполняются без сети с подставными портами. Тесты адаптеров проверяют преобразование payload и обработку ошибок. Архитектурные тесты контролируют направление импортов, отсутствие циклов и запрет чужого приватного хранилища. Реальная интеграционная проверка — отдельный opt-in, по умолчанию без записи в личные данные.

Существенные решения фиксируются в ADR: контекст, выбор, альтернативы и последствия. AGENTS.md требует читать эту архитектуру перед изменениями. Тесты в `tests/architecture` закрепляют направление импортов, независимость бизнес-кода и отсутствие циклов. Они проверяют явные Python-импорты; динамические импорты ими не анализируются.
